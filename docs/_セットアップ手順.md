## 手順

### 1. Railsアプリのルートに配置する

すでにRailsアプリがあるなら、そのルートに `docs/` と `CLAUDE.md` `README.md` を置くだけでよい。

```bash
cd 既存のRailsアプリ/
# ダウンロードした docs フォルダ、CLAUDE.md、README.md をここに置く
```

### 2. 画像のパスを崩さない

**`docs/images/` の4枚は、`docs/仕様書_MVP.md` から `images/screen1_...` という相対パスで参照している。**

ダウンロード時に画像がバラバラの場所に落ちてくることがある。**`docs/images/` というフォルダを自分で作って、4枚をその中に入れること。** これが崩れると画像が表示されない。

### 3. `.gitignore` を確認する

```bash
grep sqlite .gitignore
```

Rails 8標準の `.gitignore` には `/storage/*`（DBファイルの置き場である `storage/` ごと除外）が入っているが、念のため確認する。**DBファイルがリポジトリに混入すると「本番データをGitに上げる人」に見える。**

入っていなければ追記する。

```
/storage/*
!/storage/.keep
```

### 4. コミットする

```bash
git add .
git commit -m "設計ドキュメントとCLAUDE.mdを追加"
```

**改修に着手する前に必ずコミットしておくこと。** 主動線の入れ替えで画面①を作り直すため、戻れる場所が必要になる。

### 5. Claude Code を起動する

リポジトリのルートで起動すれば `CLAUDE.md` が自動で読まれる。

```
docs/仕様書_MVP.md の §6.6 を読んで、
画面①を週カレンダー方式に作り直したい。

まず現状の MeetingsController と関連ビューを確認して、
変更が必要な箇所を洗い出すところまでやって。実装はまだしないで。
```

**「実装はまだしないで」を入れること。** いきなり書き始めると、何が変わったか把握できないまま大量のコードが入る。**最終レビューで質問されるのは自分である。**

## 表示の確認

### GitHub

**Mermaidも画像も、何も入れずに表示される。** push して `docs/仕様書_MVP.md` を開けばよい。一番確実。

### VS Code

1. **フォルダを開く**（ファイル単体で開くと画像が壊れる）
2. mdファイルを開いて `Cmd+K` → `V`（Windowsは `Ctrl+K` → `V`）で横並びプレビュー
3. Mermaidを表示するには拡張機能 **Markdown Preview Mermaid Support** が必要

| 症状 | 原因 |
|---|---|
| 画像が壊れたアイコンになる | `docs/images/` の位置が違う。フォルダを開いているか確認 |
| 図が灰色のコードのまま | Mermaid拡張が未インストール、またはプレビューの開き直しが必要 |

## 提出時のチェックリスト

| | 項目 |
|---|---|
| ☐ | `README.md` の `<!-- TODO -->` をすべて埋めた |
| ☐ | 「未実装」の欄を正直に書いた |
| ☐ | `bin/setup` → `bin/rails server` で**クリーンな環境から起動できる**ことを確認した |
| ☐ | `storage/*.sqlite3` がGitに入っていない |
| ☐ | 生成されたコードをすべて読んだ（**説明できない行がない**） |
| ☐ | 過去日時での予約が通らないことを確認した |
| ☐ | 判断メモ（提出物3）を書いた |

### 判断メモに書く材料

課題文の「実装中に気づいて、設計から変えた点」に使える出来事が、すでに複数ある。

| 出来事 | 内容 |
|---|---|
| 認証の穴 | `meetings.created_by_id` を持ちながら認証をPhase 2に送っており、**取れない値を保存する設計**になっていた。簡易ログイン（F-05）をMustに追加して解消 |
| 用語のドリフト | 採用面接シナリオを題材に実装を始めたが、「採用ツールではなく汎用の時間調整ツール」との指摘を受け、DB・コード・ドキュメントの用語を全面的に一般化した（面接→ミーティング等） |
| ルール合成の未定義 | テナントと個人の `availability_rules` が競合したときの規則を決めていなかった。追加ヒヤリング（H2-04）で指摘を受け、BR-12として定義 |
| **主動線の入れ替え** | 追加ヒヤリング（H2-05）で「時間で絞るのではなくカレンダー一覧を見たい」との要件が出た。**`AvailabilityChecker`・データモデル・排他制御はいずれも変更せず、画面のみの改修で済んだ。** 判定を単一クラスに閉じ込めていた効果 |
| カレンダー連携画面 | 設計時に定義しておらず、実装中に追加した画面 |
