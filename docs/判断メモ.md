## D-1. 簡易ログインを廃し、メール＋パスワード認証（`has_secure_password`）にした

| | 内容 |
|---|---|
| 元の想定 | 仕様書§6.2／要件 F-05／別紙A A-5：`operator=true` のメンバーを選ぶだけ。パスワードなし。なりすまし可能を明示的に許容し、本認証は Phase 2（F-52） |
| 実装 | `User` に `has_secure_password`、`users.password_digest` を追加。`SessionsController#create` は `email + operator:true` で引いたうえで `authenticate` する。`reset_session` でセッション固定化を防ぎ、`DELETE /logout` を追加 |
| 変更理由 | 認証の骨格を後から差し込むと、`current_user` を前提にした全コントローラー・ビュー・テストに広く手が入る。Phase 2 の手戻りを避けるため、認可（D-2）とセットで先に土台を入れた。実装コストは小さく（`bcrypt` 追加とマイグレーション1本）、判定ロジック・排他制御・データモデルには一切波及しない |
| 据え置き | 多要素認証・パスワードリセット・ロックアウト・監査ログは Phase 2 以降。開発用は全アカウント共通パスワード（`db/seeds.rb` の `DEV_PASSWORD`） |
| 影響 | 要件§2-8（セキュリティ要件は発生しない）、仕様書§9.1-4（認証が簡易）の記述を更新。F-52 は「認証・認可の土台は Phase 1、管理者画面の完全分離とMFA・監査は Phase 2」に分解 |

## D-4. メンバー管理（F-01／F-02、画面③）を実装した

- 仕様書§6.4・§9.4・§7・要件§2-4 は「未着手、`db/seeds.rb` 投入のみ」としていたが、`resources :users` のフルCRUDと `UsersController`、`app/views/users/` を実装済み。admin 限定（D-2）。
- **ユーザー削除の制約**：`User has_many :created_meetings, dependent: :restrict_with_exception`。登録者になっているミーティングが残っているメンバーは削除できない（`created_by_id` が NOT NULL のため、消すと孤児レコードになる）。UI は `ActiveRecord::DeleteRestrictionError` を捕捉して理由を表示する。
- 自分自身（`current_user`）は削除不可。ログイン中のセッションが宙に浮くのを防ぐため。
- 編集時、パスワード欄が空なら `password_digest` を更新しない（`UsersController#update_params`）。

## D-5. 予約の変更（F-25）・キャンセル（F-26）を Phase 1 に前倒しした

| | 内容 |
|---|---|
| 元の想定 | 要件§3-2・§5-1・§5-2：F-25／F-26 は **Phase 2**。「H-32・H-33 未回答」「作成が動かなければ変更対象も無い」を理由に外していた |
| 実装 | `MeetingsController#edit / #update / #destroy`。`edit.html.erb` を追加 |
| ~~**参加者の変更は含めない**~~（→ D-14 で撤回） | 変更できるのは日時・所要時間・ゲスト情報（`guest_name` / `location_type` / `location_text` / `meet_url`）のみ。**出席者を増減したい場合はキャンセルして組み直す運用**とする。参加者を可変にすると「追加された人だけ再判定」「外された人の占有だけ削除」といった部分操作が増え、`confirm_booking` と別ロジックになりやすい。BR-06（1名でも不可なら全体中止）の一貫性を保つため、変更の対象を日時に絞った。**この判断は D-14 で撤回し、参加者も変更できるようにした**（懸念していた部分操作は `sync_attendees_and_events!` に閉じ、再判定は従来どおり全員まとめて1回で済んだ） |
| 変更時の再判定（`confirm_update`） | `confirm_booking` と同じ `AvailabilityChecker` を使う。ただし判定対象の予定から **このミーティング自身の占有（`calendar_events`）を除外**する。除外しないと、日時を1分も動かさず再送しただけで「自分の既存予定と重なる＝不可」になってしまう |
| キャンセル（`destroy`） | `Meeting` の `dependent: :destroy` により `meeting_attendees` と `calendar_events`（占有）が連動削除される。`source:"app"` の行だけが対象で、外部予定（`external`）には触れない（仕様書§3.3-3） |
| 変更理由 | 一覧（D-3）を出した時点で「間違えた予約を直す」導線が無いと実運用が回らない。既存の再判定機構をほぼそのまま使えるため、追加コストが小さかった |
| 据え置き | ゲストへの変更通知・キャンセル通知は送らない（A-3）。変更履歴も持たない |

## D-6. 過去日時バリデーションを `on: :update` にも広げた

- 仕様書§9.3-1／別紙A A-3 のコード例は `on: :create` のみ。実装は `on: %i[create update]`（`app/models/meeting.rb`）。
- 理由：D-5 で変更を可能にした結果、`create` と同じ穴（過去日を指定すると空き判定を素通りする）が `update` にも開いたため。

## D-7. `AvailabilityChecker` に `tenant_rules:` 注入口を追加した

- 別紙A A-2 の骨子コードは `initialize(start_at:, end_at:)`。実装は `initialize(start_at:, end_at:, tenant_rules: nil)`。
- 未注入ならインスタンス内で1回だけクエリしてメモ化。週カレンダーは区間ごとに `new` するため、呼び出し側（`WeeklySlotFinder` / `confirm_booking`）で1度読んで注入し、テナントルールのクエリ回数を1回に抑える（A-2-4 のN+1対策と同じ趣旨）。判定ロジック自体は不変。

## D-8. 今後のミーティングに出席予定の参加者は削除できないようにした

| | 内容 |
|---|---|
| 見つかった穴 | `User has_many :meeting_attendees, dependent: :destroy` ＋ `has_many :calendar_events, dependent: :destroy`。登録者（`created_by`）は D-4 で `restrict_with_exception` により守っていたが、出席者側にはDB制約もアプリ側のガードも無かった。admin がうっかり出席予定の参加者を削除すると、そのミーティングの出席者と占有（`calendar_events`）だけが黙って消え、ミーティング本体（`meetings` 行）だけが残る |
| 実装 | `UsersController#destroy` で `@user.meetings.upcoming.exists?`（`Meeting.upcoming` スコープ＝`start_at >= Time.current`）を削除前にチェックし、該当すれば `ActiveRecord::DeleteRestrictionError` と同じ体裁のエラーメッセージで拒否する |
| モデル側で `restrict_with_exception` にしなかった理由 | 「未来のミーティングか」は `meeting_attendees` 単体では判定できず、関連先 `meetings.start_at` を見る必要がある。AR の `dependent: :restrict_with_exception` は関連の存在有無しか見られないため、コントローラー側で明示的にチェックする方針にした。過去のミーティングにしか出席していない参加者は、これまで通り削除できる（履歴を理由に永久に削除不可にするのは過剰と判断） |
| 影響範囲 | `UsersController#destroy` のみ。判定ロジック・排他制御・データモデルには波及していない |

## D-9. 予約変更（F-25）にも週カレンダーを添え、クリックで日時を選び直せるようにした

| | 内容 |
|---|---|
| 元の状態 | `edit.html.erb` は日付・開始時刻・所要時間を手入力するだけのフォームだった。空き状況が見えないまま日時を打ち込み、`confirm_update` の再判定で弾かれて初めて埋まっていると分かる作りで、新規予約（画面①・①b）とのUX差が大きいという指摘を受けた |
| 実装 | `MeetingsController#edit` で画面①と同じ `WeeklySlotFinder` ／ `_week_grid` パーシャルを使って週カレンダーを描画する。空き帯をクリックすると `edit` 自身に `start_at`/`end_at` 付きで戻り、フォームの日時を（保存せず）差し替える。参加者はこのミーティングの出席者に固定（D-5の方針のまま増減しない）ため、画面①のような参加者チェックボックスは無く、サイドバーは所要時間のみ |
| `_week_grid` の汎用化 | パーシャルが `new_meeting_path` / `calendar_meetings_path` を直書きしていたため、画面①からしか呼べなかった。呼び出し側から `week_path` / `slot_path`（時刻を渡すとURLを返すProc）と任意の `slot_turbo_frame` をローカル変数として渡す形に変え、画面①用（Turbo Frame内で`new_meeting_path`へ）と編集画面用（フルページ遷移で`edit_meeting_path`へ）の両方から共通利用できるようにした |
| 自分自身の占有を除外 | このミーティング自身の `calendar_events`（出席者の占有）を含めたまま空き判定すると、今の時間帯にすら「予定あり（自分自身）」で不可と出てしまう。`attach_week_events` に `exclude_meeting:` を追加し、編集画面のカレンダー描画時だけそのミーティングの占有を除く。`confirm_update`（保存時の再判定）が既に同じ理由で自分自身の占有を除外しており、それと同じ考え方を検索時にも揃えた |
| **バグ修正**：除外を `meeting_id` の不一致ではなく `id` の除外にした | 初版の実装は `scope.where.not(meeting_id: exclude_meeting.id)` だった。`calendar_events.meeting_id` は `source: "app"` の行にしか入らず、外部予定（`source: "external"`）は必ず NULL（仕様書§3.3(2)）。SQLの `!=` はNULLとの比較が「不明」になり結果から落ちる（3値論理）ため、`WHERE meeting_id != X` は外部予定を**全部**カレンダーから消してしまっていた（テナントの `block` は `AvailabilityRule` 由来で別経路のため無事だったが、出席者の他の予定が編集画面にだけ一切出ない状態だった）。「予約変更のときもブロックされている時間は表示されるか」という確認で発覚。`where.not(id: exclude_meeting.calendar_events.select(:id))` に修正し、除外対象を id で個別指定する形にして解消した |
| 影響範囲 | `MeetingsController#edit`/`#update`、`_week_grid.html.erb`（Procベースに変更）、`edit.html.erb`。判定ロジック（`AvailabilityChecker`）・データモデル・排他制御には手を入れていない |

## D-10. 予約一覧（F-24）にゲスト名・参加者名・登録者名の横断検索を追加した

| | 内容 |
|---|---|

## D-12. 認証を Devise に移行し、主催者・参加者の自己登録（会員登録）を追加した

D-1で「Gemを入れる必要はない」とあえて選んだ判断を、ユーザーからの明示的な
要望（Devise を使いたい・主催者/参加者が自分で会員登録できるようにしたい・
確認メールは不要）を受けて見直した。

| | 内容 |
|---|---|
| Gem | `devise` ＋ `devise-i18n`（アプリ全体が日本語UIのため、Deviseの標準フラッシュメッセージも日本語化する）。`bcrypt` は引き続き必要（`database_authenticatable` もbcryptを使う） |
| 有効なモジュール | `:database_authenticatable, :registerable, :rememberable, :validatable`。`:confirmable` は入れない（確認メール不要という要件そのもの）。`:recoverable` も入れない（パスワードリセットメールを送るメール基盤が無く、依頼の範囲外） |
| マイグレーション | `password_digest` を `encrypted_password` へ**リネーム**（新規カラム追加ではない）。`has_secure_password` とDeviseの `database_authenticatable` はどちらもbcryptベースでハッシュ形式に互換性があるため、既存（シード含む）のパスワードはリセット不要でそのまま使える |
| ルーティング | `devise_for :users, path: "auth"`。既に `resources :users`（管理者限定のメンバー管理CRUD・D-4）が `/users` を使っており、Devise標準の `devise_for :users`（パス指定なし）のままだと `/users/sign_in` 等が衝突するため、`/auth` 以下に分けた。ルート名（`sign_in`/`sign_up`/`sign_out`）はDevise標準のままカスタマイズしていない |
| operatorのみログイン可、という制約の移設場所 | 旧 `SessionsController#create` の `User.find_by(email:, operator: true)` と同じ制約を、`User.find_for_database_authentication` のoverrideとして認証の入口に移した。participant限定のアカウントはパスワードが合っていてもログインできない、という現行の挙動とセキュリティ姿勢（＝アカウントの存在を明かさない）をそのまま保っている |
| **権限を落とした瞬間にログイン状態が切れる、という性質の再実装** | 旧実装は毎リクエスト `operator: true` を条件にDBを引き直す `current_user` を使っていたため、admin が誰かの `operator` を `false` にした瞬間、次のリクエストから即座に弾かれた（仕様書§6.2）。DeviseはWardenのセッションを毎リクエストDBへ問い合わせ直すわけではないため、`find_for_database_authentication` の制約だけではこの性質が失われる。`ApplicationController#require_operator!` を追加し、`authenticate_user!` の直後に毎リクエスト `current_user.operator?` を確認、falseなら `sign_out` してログイン画面へ戻す形で復元した |
| admin自己付与の防止 | 自己登録フォームで許可するパラメータは `configure_permitted_parameters`（`ApplicationController`）で `%i[name operator participant]` に絞っており、**`admin` はここに含めていない**。これがadminを自己登録で絶対に付与できないようにする唯一の境界（`admin` パラメータを紛れ込ませても無視されることをテストで確認済み） |
| 自己アカウント削除の無効化 | Deviseの `registerable` はデフォルトで自己アカウント削除（`DELETE /auth`）も持つが、これを有効にすると D-8 で塞いだ穴（今後のミーティングに出席予定の人が消えると、そのミーティングの出席者・占有だけが黙って消える）が自己削除という別経路から再び開く。`RegistrationsController#destroy` を上書きし、「アカウントの削除は管理者にご依頼ください」と案内するだけにした。削除はadminのメンバー管理（D-4）に一本化している |
| `Devise::SessionsController` を素のまま使った理由 | operatorへの絞り込みをモデル層（`find_for_database_authentication`）に移したため、カスタムのセッションコントローラーが不要になった。ビュー（`app/views/devise/sessions/new.html.erb`）だけ、既存の `.session-new` の見た目に合わせて書き直している |
| `ApplicationController` の `unless: :devise_controller?` | `authenticate_user!`/`require_operator!` をグローバルな `before_action` にすると、Devise自身のログイン・登録画面（`ApplicationController` を継承する）もその対象になり、「ログインしていないとログイン画面に辿り着けない」無限リダイレクトになる。Devise自身のコントローラーはこの2つのbefore_actionから素通しにし、ログイン前提でよいアクションの出し分けはDevise本体に任せている |
| テストの書き方 | `Devise::Test::IntegrationHelpers#sign_in`（Wardenのセッションを直接操作する公式のテスト用ヘルパー）を試したが、同じテスト内で `ActiveRecord::RecordNotFound` 由来の404レスポンスを2回続けて受けると、3回目以降のリクエストで認証が外れる現象を確認した（実際に `user_session_path` へPOSTする方式では再現しないため、Wardenのテストモード固有の問題で実際のログインフローには影響しない）。再現条件を踏まないよう気をつけるより確実な方を選び、`test/test_helper.rb` の共通 `sign_in(user)` ヘルパーは実際に `user_session_path` へPOSTする方式にした |
| 影響範囲 | `Gemfile`、マイグレーション1本、`app/models/user.rb`、`config/routes.rb`、`config/application.rb`（`config.i18n.default_locale = :ja`）、`application_controller.rb`、`sessions_controller.rb`（削除）、`registrations_controller.rb`（新規）、`views/devise/*`（新規）、`layouts/application.html.erb`（ログアウトのパスのみ）、テスト各種。`AvailabilityChecker`・`WeeklySlotFinder`・予約確定/変更ロジック・データモデル（users以外）には一切手を入れていない |

## D-13. テナント全体の設定（営業時間＋固定ブロック）を1画面に集約した

D-11で「今回の依頼は固定ブロックに絞られていた」としてあえて対象外にした
allow（営業時間・F-11）の編集を、ユーザーからの明示的な要望
（「テナント設定はこちらに一元化したい」）を受けて追加した。

| | 内容 |
|---|---|
| 元の状態 | テナント全体の `block`（固定ブロック）だけが `/tenant_blocks` で編集でき、`allow`（営業時間）は `db/seeds.rb` 投入か `rails console` でしか変更できなかった。テナント全体の設定なのに、片方だけ画面があり片方は無いという状態だった |
| 画面構成 | 「営業時間」と「固定ブロック」を**別タブにせず、`/tenant_rules` の1画面に2セクションで並べた**。この2つは BR-12 で合成されて初めて「予約できる時間帯」が決まる（allowで枠を決め、blockで穴を開ける）ため、片方だけを見て編集すると結果を誤る。設定ナビのタブは「メンバー管理／テナント設定」の2つになった |
| コントローラーの統合 | `TenantBlocksController` を `TenantRulesController` に統合した（`resources :tenant_rules, except: [:show]`）。allow用・block用に2つのコントローラーを作ると、`user_id: nil` に絞るガードと `params.expect` が2箇所に分かれる。**扱うレコードが同じ `availability_rules` である以上、入力口は1つにする**方が食い違いが起きない |
| `rule_type` の決まり方 | 新規は URL のクエリ（`/tenant_rules/new?rule_type=allow`、POST も `?rule_type=allow`）、編集は既存レコードの値。**`params.expect` の許可リストに `rule_type` を入れていない**ため、フォームに `rule_type` を紛れ込ませても無視される（＝この画面から allow を block にすり替えられない）。allow/block 以外の値は `presence_in` で弾いて404。テストで確認済み |
| 個人ルールへの誤操作防止 | D-11 の `set_tenant_block`（`tenant_wide.blocks`）を `set_tenant_rule`（`tenant_wide`）に緩めた。allow も扱う以上 `.blocks` は外さざるを得ないが、**`tenant_wide`（`user_id: nil`）の絞り込みは残している**ため、URLのidを個人ルールに差し替えても404になる性質は変わらない |
| 「営業日外」を行として見せた | 営業時間の表は allow ルールのある曜日だけでなく**日〜土の7行すべて**を出し、ルールが無い曜日は「営業日外」と表示する。`AvailabilityChecker#business_hours_reason` は allow が1件も無い曜日を「営業日外」として終日不可にするが、これは「レコードが無い」という**不在で表現された仕様**で、一覧から消すと設定者から見えなくなる（変えてはいけない設計判断6と同じ理由）。削除の確認文にも「この曜日の時間帯がすべて無くなると営業日外になります」と入れた |
| ラベル欄を block だけに出した | `label` は「予約不可時間（昼休み）」のように**不可の理由**として画面に出るもので（`blocked_reason`）、allow 側は判定でも表示でも参照されない。入れられるが意味を持たない入力欄は出さない |
| 影響範囲 | `TenantRulesController`（`TenantBlocksController` を置き換え）・`views/tenant_rules/*`・`helpers/tenant_rules_helper.rb`（新規）・`layouts/_settings_nav.html.erb`・`config/routes.rb`・CSS少々。**`AvailabilityChecker`・`WeeklySlotFinder`・データモデル・排他制御には一切手を入れていない**（このコントローラーは既存の `availability_rules` テーブルへの入力口を1つ増やすだけで、判定側は元々 allow をテナント／個人の両方で読んでいる） |

## D-14. 予約変更（F-25）で参加者を選び直せるようにした

D-5で「出席者の増減はキャンセルして組み直す運用」としてあえて対象外にした参加者の変更を、
ユーザーからの明示的な要望（「もう一回候補者から選べるようにしたい」）を受けて実装した。

| | 内容 |
|---|---|
| 元の状態 | 変更画面（`/meetings/:id/edit`）で変えられるのは日時・所要時間・ゲスト情報だけ。参加者を1人足す・外すだけでも、いったんキャンセルして最初から組み直す必要があった |
| 画面 | 画面①と同じ**サイドバーの参加者チェックボックス**を変更画面にも置いた。チェックすると即座に週カレンダーが引き直され（`onchange` でGET送信）、その参加者全員が空く枠が緑で出る。選び直しの導線は画面①と同じくサイドバー一本に限る（仕様書§6.4：カレンダー本体からは操作させない） |
| 「初回表示」と「全員のチェックを外した」の区別 | チェックボックスは1つも選ばれていないとキー自体が送られないため、`user_ids` の有無だけでは両者を区別できない。サイドバーとPATCHフォームの両方に**空文字の `hidden_field_tag "user_ids[]"` を1つ置き**、`edit_user_ids` が `params.key?(:user_ids)` で判定する（キー無し＝初回表示または日時だけを送る旧来の形＝参加者は現状維持、キーあり＝送られた内容そのまま） |
| 週送り・空き帯クリックでの引き継ぎ | `week_path` / `slot_path` に `user_ids` を載せる。載せないと週を送った瞬間に `params[:user_ids]` が消え、選び直した参加者が現在の出席者へ戻ってしまう |
| 選んだ日時の保持 | サイドバーに `start_at` の hidden field を追加した。参加者や所要時間を変えるとフォーム全体がGETで再送されるため、これが無いと空き帯で選び直した日時が保存前に元の予約日時へ戻る（D-9 で日時だけを扱っていた頃からあった挙動を、参加者の選び直しと組み合わせて使えるように直した） |
| **再判定は従来どおり1回**（BR-06） | `confirm_update` の判定対象を「このミーティングの既存出席者」から「**送信された参加者**」に変えただけ。新しく追加された人も同じ `AvailabilityChecker` を1回通り、1名でも不可なら変更全体を中止する。D-5 で懸念した「追加された人だけ再判定」のような部分操作は入れていない |
| 出席者・占有の作り直し（`sync_attendees_and_events!`） | 「残す人以外の `meeting_attendees` と `calendar_events` を消す → 残す人は時刻・タイトルを更新、増えた人は `source: "app"` で新規作成」の順で揃える。**外した人の占有を消し忘れると、出席しないミーティングの占有だけがその人のカレンダーに残って以後の空き判定を誤らせる。追加した人の占有を作り忘れると、次の検索でその人が空いていることになりダブルブッキングする**（変えてはいけない設計判断3と同じ理由）。トランザクション内なので、途中で失敗すれば増減も日時変更も丸ごと巻き戻る |
| 参加者の絞り込み | `User.where(id: @user_ids, participant: true)` として、`participant` でないIDが送られても無視する（`confirm_booking` と同じ）。テストで確認済み |
| 影響範囲 | `MeetingsController`（`edit` / `update` / `load_edit_calendar` / `confirm_update` / 新規 `edit_user_ids`・`sync_attendees_and_events!`）、`views/meetings/edit.html.erb`、`_week_grid.html.erb`（案内文のみ）。**`AvailabilityChecker`・`WeeklySlotFinder`・データモデル・排他制御の仕組みには手を入れていない**（判定は「このメンバーはこの区間に空いているか」を答えるだけで、誰を渡すかを知らないため） |

## D-15. users の3フラグを廃止し、「管理者」と「メンバー」の2区分にした

ユーザーからの要望（「主催者・参加者・管理者の3つを、管理者とメンバーで良い」）を
受けて、`users.operator` と `users.participant` を落とし、`users.admin` だけを残した。

| | 内容 |
|---|---|
| 元の状態 | `operator`（ツールを操作する）／`participant`（ミーティングに出る）／`admin`（設定画面を操作できる）の3フラグ。「主催者が自分でもミーティングに出る」兼任を役割テーブルではなくフラグで表現するための設計だった（仕様書§6.1） |
| 廃止の理由 | 兼任を表せるようにした結果、**実運用では両方 true のアカウントしか作られず、区別が設定項目としてだけ残っていた。** シードで唯一 `participant: false` だった「調整専門の主催者」も、他人の予定を見て枠を押さえる以上、自分が候補に並んで困る場面が無い。**表現できるが誰も使い分けない区別は、設定画面の項目とテストの分岐を増やすだけ**と判断した |
| 新しい区分 | **アカウントを持つ人＝メンバー。** ログインでき、ミーティングの参加者候補にも並ぶ。その上に `admin`（設定を操作できる）が1段乗るだけ |
| マイグレーション | `SimplifyUserRoles`（`remove_column` 2本）。`admin` は残すので既存の管理者はそのまま |
| **失われた性質1：ログインを止める手段** | `operator: false` にすればアカウントを残したままログインだけ止められたが、これができなくなった。**アクセスを止める手段はメンバーの削除（管理者のメンバー管理）に一本化される。** 退職者などをアカウントごと消せない事情が出てきたら、`active` のような別フラグを足すことになる（今回は要望に無いので作らない） |
| **失われた性質2：権限を落とした瞬間にログイン状態が切れる** | D-12 で `require_operator!` として復元した性質だが、`operator` 自体が無くなったため一緒に削除した。`admin` を落とす操作は残るが、こちらは `require_admin` が毎リクエスト `current_user.admin?` を見るため、落とした瞬間から設定画面に入れなくなる性質は保たれている |
| 参加者候補の絞り込み | `User.where(participant: true)` → `User.order(:name)`、`User.where(id: @user_ids, participant: true)` → `User.where(id: @user_ids)`。**主催者自身も候補に並ぶ**（兼任のケースではむしろ自然） |
| 自己登録フォーム | 役割のチェックボックスを外した。許可パラメータは `%i[name]` だけになり、**`admin` を許可リストに入れないという境界（D-12）はそのまま**残っている |
| 影響範囲 | マイグレーション1本、`app/models/user.rb`、`application_controller.rb`、`users_controller.rb`、`meetings_controller.rb`（ユーザー取得のクエリのみ）、`views/users/*`・`views/devise/registrations/new`、`db/seeds.rb`、テスト各種。**`AvailabilityChecker`・`WeeklySlotFinder`・排他制御・`availability_rules`・`meetings` 周辺には一切手を入れていない**（判定は渡されたユーザーを見るだけで、そのユーザーがどう選ばれたかを知らないため） |
