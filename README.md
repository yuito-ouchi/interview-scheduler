# ミーティング調整ツール

社内の時間調整を行うツール。技術課題として実装。**採用面接専用ではなく、汎用の日程調整ツール**として用語を統一している（実装は元々「採用面接の日程調整」を題材に始めたが、途中でドメインを汎用化した。詳細は判断メモ）。

---

## 何を解決するツールか

主催者は、ゲストからメールで届く希望日時に対して、社内メンバーのカレンダーを一人ずつ開いて空きを確認している。困りごとは「確認の工数」と「予定の重複」の2つだが、**原因は1つで、確認と予約が分断されていること**にある。確認した瞬間から登録するまでの間、誰も空き状況を見ていない。

**本ツールは、確認から予約までを一度の操作で完結させ、確認工数と重複を同時に消す。**

---

## 起動手順

### 前提

| | バージョン |
|---|---|
| Ruby | 3.2 以上 |
| Rails | 8.1 |
| DB | SQLite3（**別途インストール不要**） |

### 手順

```bash
git clone <このリポジトリのURL>
cd <リポジトリ名>

bin/setup          # 依存関係のインストール、DB作成、マイグレーション、seed投入
bin/rails server
```

ブラウザで `http://localhost:3000` を開く。

### 初回の操作

1. 操作者選択画面が表示される。**パスワードは不要**（後述の「認証について」参照）
2. 任意の主催者を選ぶ（例：採用 花子）
3. 「ミーティングを組む」の右サイドバーで参加者をチェックし、週カレンダーで空き枠をクリックする

### 投入されるダミーデータ

`db/seeds.rb` で以下が作られる（`bin/rails db:seed` で再投入可能）。

| 種別 | 内容 |
|---|---|
| メンバー | 主催者2名（うち1名は参加者兼任）、参加者4名。計6名 |
| 既存予定 | 今週〜来週の範囲に15件（うち終日1件）。区間の境界条件（別紙A A-2-5）を検証できる配置 |
| 営業時間 | 平日 10:00〜18:00 を allow、12:00〜13:00 を block（昼休み）。土日は allow なし＝予約不可 |

### 意図的に作っていないもの

**時間切れではなく、スコープ判断として外したもの。** 判断根拠は `docs/要件定義書_Phase別.md` §5-2 に記載。

| 項目 | 外した理由 |
|---|---|
| ゲスト向けの予約ページ | 追加ヒヤリングで「期日的に間に合うのであれば」と条件付きだった。公開URL・仮押さえ・排他制御が芋づる式に必要になり、工数の大半を消費する。**中核を確実に動かす方を優先した** |
| Googleカレンダー実連携 | 「ダミーデータで再現して、同期された前提で進めて良い」と合意済み |
| ゲストへのメール送信 | 連絡文面の運用を聞けておらず仕様を決められない |
| 予約の変更・キャンセル | 変更頻度をヒヤリングできていない |
| 会議室の予約 | 会議室管理の要否が未確認。押さえるリソースが2種類になり判定が倍の複雑さになる |
| パスワード認証・権限制御 | 本番データを扱わずセキュリティ要件が発生しない |

## 設計上の要点

**詳細は仕様書を参照。ここでは4点だけ挙げる。**

### 1. 空き判定を単一クラスに集約している

`app/services/availability_checker.rb` に閉じ込め、**検索時と予約確定時の両方から同じクラスを呼ぶ。**

このツールの重複防止は「確定直前に同じ判定をやり直す」仕組みで成立している。判定が2箇所にあると、片方だけ修正されて食い違い、**再チェックそのものが意味を失う。**

### 2. 予約すると `calendar_events` にも書き込む

`meetings` は業務の記録、`calendar_events` は時間の占有で、**別の事実**である。1件のミーティングから出席者の数だけ占有が生まれる。

書かないと、次の検索で自ツールが入れたミーティングが空き判定から漏れ、**自分が入れた予定に自分でダブルブッキングする。**

### 3. 空いていない枠も理由付きで表示する

相談者は現在、誰がなぜ空いていないかを目視で把握している。**空いているものだけを表示すると、その情報が失われる。** 実装時には、あと1人だけ埋まっている枠も理由付きで示す「あと1人で空き」表示を追加した（仕様書§6.4）。

### 4. 用語を「ミーティング」に統一している

DB・コード・テスト全体で「面接／候補者／面接官／採用担当者」ではなく「ミーティング／ゲスト／参加者／主催者」を使う。実装完了後に「採用ツールではなく汎用の時間調整ツール」との指摘を受け、テーブル名・カラム名を含めて一括リネームした（判断メモ参照）。ヒヤリング質問リストのみ、実際の記録として旧用語のまま残している。

## 認証について

**パスワード認証を実装していない。** 操作者を選択してセッションに保持するだけで、**他人になりすませる。**

社内利用であり本番データを扱わないため、Phase 1 では意図的に許容している。**実装漏れではなく判断である。** 認証・権限制御は Phase 2（`docs/要件定義書_Phase別.md` §3-2 の F-52）。

## 既知の制約

`docs/仕様書_MVP.md` §9 に一覧。主なものは以下。

| 項目 | 内容 |
|---|---|
| 「動かせる予定」を区別しない | 調整可能かを機械的に判定する手段がない（仮定A-1） |
| 過去のミーティングを参照する画面がない | 一覧は今後分のみ。データと占有は残る |
| 祝日を扱わない | 祝日マスタの調達方法が未確認 |
| タイムゾーンはJST固定 | 社内利用のため |
