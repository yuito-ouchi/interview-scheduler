## 何を解決するツールか

採用担当者は、候補者からメールで届く希望日時に対して、社内メンバーのカレンダーを一人ずつ開いて空きを確認している。困りごとは「確認の工数」と「予定の重複」の2つだが、**原因は1つで、確認と予約が分断されていること**にある。確認した瞬間から登録するまでの間、誰も空き状況を見ていない。

**本ツールは、確認から予約までを一度の操作で完結させ、確認工数と重複を同時に消す。**

### 意図的に作っていないもの

**時間切れではなく、スコープ判断として外したもの。** 判断根拠は `docs/要件定義書_Phase別.md` §5-2 に記載。

| 項目 | 外した理由 |
|---|---|
| 候補者向けの予約ページ | 追加ヒヤリングで「期日的に間に合うのであれば」と条件付きだった。公開URL・仮押さえ・排他制御が芋づる式に必要になり、工数の大半を消費する。**中核を確実に動かす方を優先した** |
| Googleカレンダー実連携 | 「ダミーデータで再現して、同期された前提で進めて良い」と合意済み |
| 候補者へのメール送信 | 連絡文面の運用を聞けておらず仕様を決められない |
| 予約の変更・キャンセル | 変更頻度をヒヤリングできていない |
| 会議室の予約 | 会議室管理の要否が未確認。押さえるリソースが2種類になり判定が倍の複雑さになる |
| パスワード認証・権限制御 | 本番データを扱わずセキュリティ要件が発生しない |

## 設計上の要点

**詳細は仕様書を参照。ここでは3点だけ挙げる。**

### 1. 空き判定を単一クラスに集約している

`app/services/availability_checker.rb` に閉じ込め、**検索時と予約確定時の両方から同じクラスを呼ぶ。**

このツールの重複防止は「確定直前に同じ判定をやり直す」仕組みで成立している。判定が2箇所にあると、片方だけ修正されて食い違い、**再チェックそのものが意味を失う。**

### 2. 予約すると `calendar_events` にも書き込む

`interviews` は業務の記録、`calendar_events` は時間の占有で、**別の事実**である。1件の面接から出席者の数だけ占有が生まれる。

書かないと、次の検索で自ツールが入れた面接が空き判定から漏れ、**自分が入れた予定に自分でダブルブッキングする。**

### 3. 空いていない枠も理由付きで表示する

相談者は現在、誰がなぜ空いていないかを目視で把握している。**空いているものだけを表示すると、その情報が失われる。**

## 認証について

**パスワード認証を実装していない。** 操作者を選択してセッションに保持するだけで、**他人になりすませる。**

社内利用であり本番データを扱わないため、Phase 1 では意図的に許容している。**実装漏れではなく判断である。** 認証・権限制御は Phase 2（`docs/要件定義書_Phase別.md` §3-2 の F-52）。

## 既知の制約

`docs/仕様書_MVP.md` §9 に一覧。主なものは以下。

| 項目 | 内容 |
|---|---|
| 「動かせる予定」を区別しない | 調整可能かを機械的に判定する手段がない（仮定A-1） |
| 過去の面接を参照する画面がない | 一覧は今後分のみ。データと占有は残る |
| 祝日を扱わない | 祝日マスタの調達方法が未確認 |
| タイムゾーンはJST固定 | 社内利用のため |
